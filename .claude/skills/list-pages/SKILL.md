# 列表页面规范

## 使用范围

本规范适用于本项目的后台列表页，参考 `src/pages/BusinessRevenue/Agents`、`Orders`、`Recharges`。同时遵守 `umi-max`；根据原型转写时也遵守 `prototype-to-page`。用户对具体页面明确提出的不同布局或功能优先，不擅自批量改造其他已有页面。卡片类、看板或其他非表格原型不强制改成列表。

## 布局与查询

- 根据原型导航分组，将页面放在 `src/pages/<菜单分类>/<页面>/`，路由 path 与页面目录对应；保留现有登录页。迁移路由时同步检查登录、菜单、跳转和 model 命名空间。
- 列表优先使用项目现有 `ProTable`，分页、筛选和刷新使用实际接口；不要额外嵌套仅为包裹表格的 `className={styles.card}` 容器，也不默认增加顶部状态 Tab。确有页面专属需求或用户另有明确要求时按确认范围处理。
- 状态筛选放在 ProTable 搜索表单中，标题使用“状态”，已确认枚举使用可清除的下拉选项；选项中文供展示，查询向后端传对应原始值。接口未确认枚举时不猜测，先核实或向用户说明。
- 表格状态列复用 `src/components/PrototypeStatusTag`，根据页面已确认的状态映射显示业务中文并匹配原型颜色；未知状态保留原值，缺失值显示 `—`。不要将不同业务的状态编码或审核含义互相套用。
- 参考 `Orders` 页：客户查询记录完成情况使用 `authorizationStatus`，`pending` 显示未完成、`active` 显示已完成、`revoked` 显示已取消，不使用订单 `status`。
- 不额外添加页面错误 Alert 及重试条；保留明确且不重复的错误消息、加载和空状态，失败不能假装为成功空数据。

## 实现与核验

- 优先使用已有生成 service；不修改生成文件。复杂请求编排放页面 model，ProTable 持有列表数据；避免共享 model 全局初始化时请求，处理请求竞态、取消和离页 reset。
- 页内新增、详情、编辑及导出是否实现以用户对当前页面的授权为准；只要求提示时不发送写请求，也不虚构成功。不得在业务页面展示 Mock、开发进度或未迁移说明。
- 核对正式协议：接口路径、权限、状态、筛选项、分页参数、金额日期、响应结构和统计口径。对缺失信息明确标注，不能把原型或其他接口的枚举当作当前接口已确认。
- 检查路由、搜索参数、状态展示和分页，运行相关 lint、格式检查和构建；浏览器视觉验收、真实接口联调分别记录，未运行不能写成已通过。
